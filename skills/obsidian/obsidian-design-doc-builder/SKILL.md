# Obsidian 設計書作成スキル

## 目的

- ユーザーの要件を、実装に直結する設計書ノート群へ変換する。
- 設計書は `02-Projects/` 配下でプロジェクト単位に管理する。
- 章ごとにノートを分割し、後続の実装担当AIがそのまま着手できる粒度まで具体化する。

## このスキルを使う場面

- 新規機能・改修の設計書を作りたいとき。
- 口頭要件や箇条書き要件を、実装可能な仕様へ落とし込みたいとき。
- 設計書を章単位でレビュー・更新できる構造にしたいとき。

## 基本ルール

- 設計書プロジェクトは必ず `02-Projects/` 配下に作成する。
- 最初に章構成案を提示し、ユーザー承認を得るまで本文を書かない。
- 承認後は章ごとに `.md` を分けて出力する。
- 各ノートは `## 概要` と `## 詳細` の2部構成にする。
- `## 詳細` の小見出し構成は固定しない。ユーザー要求に応じて最適化する。
- 見出し階層、数式、ウィキリンク、タグ、フロントマターは `obsidian-vault` スキルに従う。章の骨子（`## 概要` と `## 詳細`）はこのスキルを優先する。

## フォルダ・ファイル構成

- ルート: `02-Projects/<プロジェクト名>/`
- 章ノート: 順序付きファイル名を使う
  - 例: `01-要件整理.md`, `02-アーキテクチャ.md`, `03-API仕様.md`
- 命名はVault内で一貫したパターンを維持する。

## 進行フロー

### Phase 1: 要件整理と章構成提案

1. ユーザー要求を整理し、目的・対象・前提・制約を短く要約する。
2. 章構成案を番号付きで提案する。
3. 各章に「この章で決めること」を1〜2行で添える。
4. 次の確認を行う:
   - 「この章構成で進めてよいですか？」
   - 「追加・削除・統合したい章はありますか？」

承認を得るまでPhase 2に進まない。

### Phase 2: 章別ノート作成

- 承認済み章のみ作成する。
- 章ごとに1ファイルを作る。
- 各ノートの必須骨子:
  - `## 概要`
  - `## 詳細`
- `## 詳細` の中身は、章の目的とユーザー要求に合わせて柔軟に構成する。

## 詳細セクションの設計方針（固定テンプレート禁止）

- 固定の小見出しセットを強制しない。
- ただし、実装可能性を満たすために必要な情報は不足させない。
- 章の性質に応じて、以下から必要項目を選んで構成する:
  - 仕様定義（機能・非機能）
  - 入出力・インターフェース
  - データモデル・制約
  - 処理フロー（通常系/異常系）
  - 例外・エラーハンドリング
  - セキュリティ・権限
  - テスト観点・受け入れ条件
  - 未決事項・意思決定ログ
  - 実装タスク分解

## 実装可能性の品質基準

各章の `## 詳細` は以下を満たす:

- 曖昧表現（例: 「適宜」「必要に応じて」）だけで終わらない。
- 実装判断に必要な条件・制約・前提が明示されている。
- 正常系だけでなく異常系や境界条件が定義されている。
- 検証可能な受け入れ条件がある。
- 他章依存がある場合、必要に応じて `[[ノート名]]` で参照する。

## 初回応答テンプレート

設計書作成依頼を受けた最初の応答は、次の順にする:

1. `02-Projects/<プロジェクト名>/` の作成方針
2. 章構成案（番号付き）
3. 確認質問:
   - 「この章構成で進めますか？」
   - 「追加・削除したい章はありますか？」

## 章ノート雛形

章ノートを作るときは、最低限この形から開始する:

```markdown
## 概要
- この章の目的
- この章のスコープ
- 前提・依存関係

## 詳細
- この章で必要な仕様・設計情報を、要求に応じて構成する
```

## 禁止事項

- 章構成の承認前に章本文を先行作成しない。
- すべての章で同じ小見出しを機械的に流用しない。
- `02-Projects/` 以外を設計書プロジェクトの既定保存先にしない。
