# 提案書・概算見積り下書き作成

## 目的

- 簡素な顧客向け提案書をMarkdownで作る。
- 人日ベースの見積明細を、Excelへ転記できるMarkdown表で作る。
- PPTXやExcel自体は生成しない。

## 文書の役割分担

- 提案書は顧客向けである。ITに詳しくない読者でも、何をするシステムかを理解できる粒度にする。
- 概算見積明細は、工数根拠と技術前提の置き場である。実装方式、設定値、試算条件、クラウド料金の詳細を置く。
- 提案書にAWS等のサービス名を出すことはよい。ただし、内部の挙動、API呼び出し手順、設定値、署名方式などの実装詳細は書かない。
- サービス名を出す場合も、役割が分かる短い説明にとどめる。

### 提案書に書いてよいもの

- 課題、要望、主要機能、対象外
- サービス名と役割（例: Cognitoで認証する、CloudWatch Logsに操作ログを保存する）
- お客様が判断・合意すべき前提（例: 最大利用者数、既存ドメインの利用、既存Difyの利用）
- 構成図における利用者、提案システム、外部システムの関係

### 提案書に書かず、見積明細へ移すもの

- 実装手順、内部APIの呼び出し手順、ポーリング手順
- メモリ、タイムアウト、アーキテクチャ、同時実行数などの設定値
- ピークQPS、月間リクエスト数などの試算専用数値
- クラウド利用料の試算額、Pricing Calculatorリンク、無料枠適用有無などの料金試算条件
- 署名付きURL、Function URL、OIDCトークン失効などの実装上の注意

## 適用範囲

- このスキル名をユーザーが明示した場合だけ実行する。
- 新規作成と、既存の提案書・見積明細の改訂に対応する。
- 入力には、チャットへ貼られた文章と、Cursorが読み取れる添付・Vault内ファイルを使う。
- Web検索はユーザーが明示的に依頼した場合だけ行う。

## 出力

保存先:

`02-Projects/<顧客名>/<案件名>/`

ファイル名:

- `<顧客名>-<案件名>-提案書.md`
- `<顧客名>-<案件名>-概算見積明細.md`

Windowsで使えない文字 `\ / : * ? " < > |` は、フォルダ名とファイル名から除去または全角化する。

## 進行フロー

### 1. 新規作成か改訂かを判定する

- 改訂時は既存の提案書と見積明細を先に読む。
- 利用者が手で加えた内容を、変更理由なく削除しない。
- 同名ファイルがある場合は、上書き前に必ず確認する。

### 2. 入力資料を確認する

- 入力資料から事実を抽出する。
- 数値、固有名詞、現状、要望を推測で補わない。
- 根拠がある事実の近くにMarkdownコメントを置く。

```markdown
<!-- source: [[参照ノート名]]「該当箇所」 -->
```

チャット入力を根拠にする場合:

```markdown
<!-- source: ユーザー提供情報 YYYY-MM-DD -->
```

### 3. 必須情報を集める

最初に次を確認する。

- 顧客の正式名称、組織種別、案件名
- 顧客側の課題と要望
- 提案元の会社名、部署名、担当者名

続いて、不足情報をテーマ別に3〜5問ずつ確認する。

- システム: 利用者、主要機能、対象範囲、外部連携
- 詳細: データ、セキュリティ、運用、前提条件、対象外
- 見積り: 作業範囲、機能、設計・実装・テスト人日、その他、経験則による根拠
- 日程: 想定体制、並行作業、営業日、開始条件、依存関係
- 費用: 人件費以外の既知費用

不足情報がなくなるまで生成しない。「未定」「対象外」という明示回答は確定情報として扱う。

### 4. 最終確認を取る

次を短く要約し、ユーザーの承認を得る。

- 顧客・案件・提案元
- 課題・要望・提案範囲
- 主要機能・前提条件・対象外
- 体制・期間・合計人日
- 出力先と上書き有無

承認前にファイルを作成・更新しない。

### 5. 提案書を作る

[proposal-template.md](proposal-template.md)を基準に、次の順で記述する。

1. 冒頭情報ブロック
2. 顧客組織における課題
3. ご要望
4. 提案するシステム概要
5. 提案するシステム構成
6. 詳細
7. 概算スケジュール
8. 概算見積り
9. 末尾タグ

次は追加しない。ユーザーが実行時に明示した場合だけ追加する。

- エグゼクティブサマリー
- 効果・KPI
- 導入ステップ・次のアクション

#### 表現

- 見出しと箇条書きを中心とする、簡潔なビジネス文体を使う。
- 課題と要望は簡潔な箇条書きにする。
- システム概要は2〜3文と主要機能の箇条書きにする。実装手順や内部の呼び出し方式は書かない。
- 課題・要望・提案内容の対応を内部で検査するが、対応表やIDは表示しない。
- 組織種別に応じて `貴社`、`貴財団`、`貴法人`、`貴協会` などを使い分ける。曖昧なら確認する。
- ITに詳しくない読者でも、各文の意味が通るかを確認する。

#### システム構成図

- Mermaidの `flowchart LR` を使う。
- 左から `利用者 → 提案システム → 外部システム` の順に配置する。
- 提案システムの境界を `subgraph` で示す。
- 矢印には主要なデータまたは処理を表すラベルを付ける。
- サービス名をノードに含めてよいが、役割が分かる短い名称にする。
- 図の後に、意図と主要な流れを短く説明する。実装の細部は書かない。

#### 詳細

小見出しと箇条書きで次を記述する。

- 機能
- 外部連携
- データ
- セキュリティ
- 運用
- 前提条件
- 対象外

各項目は、サービスと役割、お客様が合意すべき条件にとどめる。設定値、試算専用数値、内部手順は見積明細へ移す。

#### 概算スケジュール

`工程｜期間｜主な作業｜依存関係` の表を使う。期間は、確認済みの体制、並行作業、営業日、依存関係から算出する。

### 6. 見積明細を作る

[estimate-template.md](estimate-template.md)を使う。

- 明細表の前に `## 技術前提・実装方針` を置く。
- 提案書から外した実装詳細、設定値、試算条件、クラウド料金の根拠をここに記載する。
- 1人日を8時間とする。
- 工数を0.5人日単位で丸める。
- バッファや予備工数は既定では加えない。ユーザーが明示した場合のみ `その他` へ計上する。
- 行は機能単位とする。設計・実装・テストは同じ機能行に揃える。
- 横断作業（要件定義、結合・総合試験、受入支援、導入）は別行とし、該当列だけ埋める。
- 負荷試験は独立行にしない。結合試験のテストへ含める。
- 0人日のセルは空欄にする。
- 役割列と算出根拠列は設けない。短い根拠は備考に書く。
- 列は `No.｜機能｜設計｜実装｜テスト｜その他（要件定義、導入、バッファ）｜小計｜費用｜備考` とする。
- `小計` は設計 + 実装 + テスト + その他とする。
- 費用は空欄にする。
- 人件費以外の既知費用は別枠にし、未確定費用は `別途` と記載する。
- クラウド利用料の試算額やPricing Calculatorリンクがある場合は、人件費以外の費用または技術前提に置く。

### 7. 提案書のMock金額を算出する

- 仮単価は `50,000円／人日` とする。案件ごとに異なる単価が指定された場合はそれに従う。
- 提案書の概算見積りは工程別のままとする。明細の列合計から次で戻す。
  - 要件定義 = 機能名が要件定義の行の `その他`
  - 設計 = 設計列合計
  - 実装 = 実装列合計
  - 試験 = テスト列合計
  - 導入 = 機能名が導入の行の `その他`
- バッファを計上した場合のみ、提案書に「予備」行を足して合計を合わせる。既定では予備行を出さない。
- 工程別人日と工程別Mock金額を掲載する。
- 表示形式は `¥1,500,000（税別・Mock）` とする。
- 合計Mock金額は、見積明細の合計人日に仮単価を掛ける。
- `Mock金額・税別・人件費以外は別途・要件確定後に再見積り` と明記する。
- 見積明細へObsidian内部リンクを付ける。
- 提案書の見積条件に、クラウド料金の試算リンクやUSD目安を置かない。必要なら見積明細側に置く。

### 8. 保存前に検査する

[quality-checklist.md](quality-checklist.md)をすべて確認し、不一致は修正する。検査結果の別ファイルは作らない。

### 9. 保存する

- 新規・更新ファイルの改行コードはLFにする。
- フロントマターには `title` と `created` だけを置く。
- ノートタイトル用の `#` 見出しは使わず、メインセクションは `##` にする。
- タグはノート末尾に置く。
- 提案書には `#提案書 #プロジェクト`、見積明細には `#概算見積り #プロジェクト` を付け、案件に応じたタグを追加する。

完了時は、作成・更新した2ファイルのパスだけを簡潔に報告する。スキルファイルを更新した場合は、そのパスも報告する。
