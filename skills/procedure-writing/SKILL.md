# 手順書作成

実行者は「今何をすればよいか」だけを上から拾えればよい。知識・仕様・例外を同列に積まない。

## いつ使うか

- 手順書・インストール手順・セットアップ手順を新規に書くとき
- 既存文がごちゃついてわかりづらいとき
- 手順として読めるかをレビューするとき

## ごちゃつきの正体

次のどれかがある文書は、手順書として失敗している。

1. **文書の仕事が複数** — 仕様・API・設定・CI・デプロイ・運用が1本
2. **読者が複数** — 開発・CI・本番・相手側が同時に想定されている
3. **並びがトピック順** — 実行順ではなく、視線が折れ線になる
4. **同じ制約が散在** — 冒頭・前提・注意に同じ警告が繰り返される
5. **「やれ」と「なぜ」が同列** — 実行指示の隣に設計理由の長文がある
6. **スキャン単位がない** — 見出し → 短い指示 → コマンド、の塊になっていない
7. **本線と例外が同じ階層** — 任意・稀・更新手順が本線と同じ見出しレベル
8. **完了条件が薄い** — 何を見れば成功か、手順の横にない

## 進行

### 新規作成

1. 文書の仕事を1つにする（今日実行すること）。読者は実行する人1人。
2. 実行順に作業のかたまりを並べる。
3. 下記の書き方で本文を書く。
4. 末尾の点検リストで確認する。

### 既存文（レビュー・書き直し）

1. 上記8点で診断し、指摘を先に出す。
2. 混合していれば、`手順` / `仕様` / `運用` への分割案を出す。
3. **承認を得るまで本文を書き直さない。**
4. 承認後に書く。分割する場合、このスキルが書くのは手順側だけ。仕様・運用は中身を勝手に再設計しない。

## 必須構成

必須は **概要** と **手順** だけ。前提・確認・失敗時・付録は、規模がそれを必要とするときだけ足す。所要時間は書かない。

````markdown
## 概要

[今日やること。1文]
- [作業項目]
- [作業項目]

## 1. [作業のかたまり]

- [短い指示]

```bash
[コマンド]
```

## 2. [次の作業]
````

### 概要

- 今日やること1文と、作業項目の短い箇条書き。
- 所要時間は書かない。実行者名も、複数ロールがいない限り書かない。

### 手順

- **1見出し = 1作業のかたまり**
- **スキャン単位** は常に次の3つだけ。
  1. 見出し
  2. 短い指示（1〜3行）
  3. コマンドまたは操作
- 分岐は「この場合だけ」と本線から外す。任意作業も本線に混ぜない。
- チェックボックスは任意。長時間の手作業で進捗を追うときだけ。

### 任意セクション（必要なときだけ）

| セクション | 足す条件 |
| --- | --- |
| 前提 | 手順の外で揃えておく物がある |
| 確認 | 全体の合格条件を末尾で一度まとめたい。ステップ横の短い確認は手順内に書いてよい |
| 失敗時 | よくある落ち方と、最初に見る場所がある |
| 付録 | 本線ではやらなくてよい稀な道 |

同じ制約は1箇所にだけ書く。散らさない。

## 書き方の規則

- **動作が変わる理由だけ1行。** それ以外の「なぜ」は付録か、仕様・運用側へ。
- **秘密・環境固有値はプレースホルダ。** `<HOST>` `<IP>` `<PASSWORD>` のようにし、実パスワード・実IPを本文に書かない。置き換え指示を概要か当該ステップに1行置く。
- コマンドは指示の直後。先に長い説明を置かない。
- 見出しの並びは実行順。トピック順（ビルド・API・設定・CI・デプロイ）にしない。
- 表・YAML全文・エラーコード一覧は手順に置かない。それらは仕様側。
- 本線で使わないコマンド（更新、旧方式の撤去、稀な代替）は付録か「この場合だけ」。

## 良い例

仕事が1つ。上から実行できる。ホスト固有値はプレースホルダ。

````markdown
## 概要

HTTPS で待受けるアプリサーバを入れ、証明書と到達制限を付ける。

- JDK
- 証明書
- ファイアウォール

証明書の `<HOST>` と `<IP>` は対象サーバに合わせてから実行する。

## 1. JDK

インストーラを実行する。

## 2. 証明書

`<HOST>` `<IP>` を実値に置き換えて実行する。

```powershell
keytool -genkeypair `
  -dname "CN=<HOST>" `
  -ext "SAN=dns:<HOST>,ip:<IP>"
```
````

## 悪い例

仕事が混ざる。実行と知識が同列。同じ制約が散在する。

```markdown
## ビルド
成果物は jar。API は localhost。

## API
エラーコード表（10行）…

## 設定
YAML 全文と各キーの意味…

## CI/CD
masked 変数の理由、禁止文字、必須変数一覧…

## デプロイ
対話セッションが必要な理由（冒頭と同じ制約の再掲）
任意の Autologon、旧サービスの手動撤去、証明書更新が本線に混在
```

直し方: デプロイの実行順だけを手順書にする。API・設定・CI は仕様。制約の背景は運用。Autologon・旧撤去・証明書更新は付録か別手順。

## 点検

出す前に確認する。

- [ ] 文書の仕事は1つか
- [ ] 読者は実行する人1人か
- [ ] 見出しは実行順か
- [ ] 各手順が「見出し → 短い指示 → コマンド」か
- [ ] 同じ制約の重複がないか
- [ ] 「なぜ」は動作が変わる1行だけか
- [ ] 秘密・環境固有値がプレースホルダか
- [ ] 任意・稀な道が本線を汚していないか
- [ ] 所要時間を書いていないか
- [ ] 不要な前提・確認・失敗時・付録を足していないか
